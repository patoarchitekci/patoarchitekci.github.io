AI w SDLC: proces, nie narzędzie

Prowadził Łukasz Kałużny Protopia

Jak poukładać pracę z agentem kodującym. Tu masz wszystko, co padło na żywo: czym jest harness, jak wygląda pętla pracy, sześć zasad i linki do narzędzi. Na końcu odcinki podcastu, które rozwijają te tematy.

Czym jest harness

Prompt engineering, context engineering, teraz harness engineering. Słowa się zmieniają. Po polsku harness to uprząż. Albo chomąto: zakładasz je agentowi, żeby orał pole, czyli kodował.

Jedno słowo, trzy znaczenia

Rynek używa słowa „harness” na trzy sposoby. Stąd połowa nieporozumień w dyskusjach.

ModelClaude Sonnet, Claude Opus

To nie jest harness.

Agent kodującyClaude Code: pętla agenta, narzędzia, zarządzanie kontekstem, system prompt.

1. „Agent harness”Sam agent kodujący. Tak mówi Anthropic. To dostajesz gotowe.

Harness w Twoim repozytoriumTo, co zespół buduje wokół agenta.
GuidesZanim agent zadziała: AGENTS.md, skille, spec i plan.
SensorsPo tym, jak zadziała: hooki, lintery, testy, CI, review.

3. „Outer harness”Harness engineering: to, co zespół buduje dla swojego kodu. OpenAI, Birgitta Böckeler.Tego znaczenia używamy

2. „Everything except the model”. Znaczenia 1 i 3 razem. LangChain: „If you're not the model, you're the harness.”

Jeżeli nic nie wymusisz, to ty nie masz żadnego procesu.

Co pilnuje reguł

Reguły piszesz raz, w AGENTS.md. Agent czyta je na starcie każdej sesji. Potem pracę sprawdzają bramki, które działają bez Twojej uwagi.

robi agentdecydujesz Tysprawdza bramka

Hooki z webinaru

  • Po edycji pliku: formatter i linter, tylko na tym pliku.
  • Na koniec sesji: testy i build.
  • Pre-commit: pełne sprawdzenie. Commit przechodzi tylko na zielono.

Progi jakości zapisz jawnie: złożoność, liczba argumentów, martwy kod. Konfigurację napisze agent, Ty ją sprawdzasz.

Markdown kontra hook

  • Reguła w markdownie nic nie kosztuje, ale działa tylko wtedy, gdy model jej posłucha.
  • Hook nie zależy od modelu. Mierzy wynik i blokuje, gdy wynik jest czerwony.
  • Cena hooka: koniec tury czeka na build i testy, a skille i agenci w repozytorium zajmują kontekst.

Jedno zadanie, jedna sesja, jeden PR

Wiele zespołów opisało pracę z agentem i każdy opis to ta sama pętla. Sześć kroków: agent robi cztery, a Ty decydujesz w dwóch.

robi agentdecydujesz Ty

Dlaczego nowa sesja na każde zadanie

  1. Stary kontekst miesza zadaniaModel za każdym razem czyta całą rozmowę, razem z tym, co dotyczyło poprzedniego zadania.
  2. Stary kontekst kosztujeZa każde ponowne czytanie płacisz tokenami.
  3. Nowa sesja nic nie gubiStan jest na dysku: plik z regułami, ticket, plan i commity.
  4. Mały PR da się zreviewowaćJedno zadanie daje jeden mały pull request.

Flow na skillach Matta Pococka

Tak wyglądało demo. Każdy skill to jeden krok, a po każdym kroku zostaje plik. Skille są małe, więc łatwo je zmienić pod swój zespół.

robi agentdecydujesz Typlik, który zostaje

Czemu tak

  • Wywiad na start. Najczęstsza porażka to nieporozumienie: agent zbudował coś innego, niż chciałeś.
  • Spec przed kodem. Agent dostaje wszystko na tacy i nie przeszukuje repozytorium na ślepo.
  • Małe kroki. Większą zmianę dzielisz na tickety, małą puszczasz od razu do implementacji.
  • Dwa sposoby implementacji. /implement robi spec albo tickety w jednej sesji. /implement-spec bierze cały spec na jeden branch i puszcza subagentów równolegle.
  • Review na końcu. Agent sprawdza kod ze specem, a Ty dostajesz PR z dowodami.

Do speca warto dopisać sekcje techniczne: zmiany w kodzie, kontrakty, model danych, failure modes i decyzje o testach.

Słownik: ubiquitous language z DDD

  • /grill-with-docs sprawdza Twoje słowa ze słownikiem w GLOSSARY.md i dopisuje nowe pojęcia w trakcie wywiadu.
  • W demo słownik nie znał operacji „Zamknij”. Ustalenie: akcja nazywa się „Kill”, a „Close” zostaje dla zamykania zakładki.
  • Zmienne, funkcje i pliki dostają te same nazwy, więc agent łatwiej porusza się po kodzie.
  • Agent pisze krócej i zużywa mniej tokenów, bo jedno pojęcie zastępuje długi opis.

Sześć złotych zasad

  1. 1

    Jeden task, jedna sesja, jeden PR

    Każde zadanie zaczynasz w nowej sesji, w folderze projektu.

  2. 2

    Dopracuj pomysł, zanim zaczniesz

    Niech agent przeprowadzi z Tobą wywiad. Garbage in, garbage out.

  3. 3

    Dwie poprawki tego samego i /clear

    Trzeci krok to nowa sesja i lepszy prompt.

  4. 4

    Unikaj długich sesji

    Jakość spada, zanim zapełni się okno kontekstu.

  5. 5

    Zapytaj agenta, jak to działa

    Nie zgaduj. Agent przeczyta pliki za Ciebie.

  6. 6

    Zapytaj, jak to zmienić, i daj się poprawić

    Powiedz, co chcesz osiągnąć. Zapytaj o słabe punkty.

Zasady 1 i 2 dotyczą startu zadania. Zasady 3 i 4 pilnują czystej sesji. Zasady 5 i 6 mówią, jak pytać agenta.

Prompt do zasady 2

Interview me about this before we plan anything: <your idea, or the Jira key>
Ask one question at a time. Give a recommended answer for each question.
Read the ticket and the code first when they can answer a question.
Write no code and no files. Stop when the idea is clear, and give me a summary for the ticket.

Do wywiadu nie potrzebujesz skilla. Odpowiedz na każde pytanie, możesz się nie zgodzić albo napisać „nie wiem”. Samo zadanie zrób już w nowej sesji.

Prompt do zasady 5

I am new in this repository and I do not know how the coding agent is set up here.
Read AGENTS.md, the agent configuration folder and docs/ first.
Tell me in 10 lines: what runs automatically, which commands I can type, and where the rules are.
Then give me 3 things to try first.

Dobre pierwsze pytanie brzmi: „Nie wiem, jak to działa ani gdzie szukać”. Nie musisz znać nazw plików.

Higiena kontekstu

Context poisoning

Agent przyjął błędne założenie. Twoja poprawka trafia do rozmowy, ale błędne założenie dalej w niej siedzi, a model czyta jedno i drugie.

  • Trzeci raz tłumaczysz to samo.
  • Masz ochotę nakrzyczeć na agenta. Mocniejsze słowa nie pomogą.
  • Napisz jednym zdaniem, co ma być inaczej. Zrób /clear. Wklej ticket i to zdanie.

Context rot

Im więcej tokenów, tym mniej precyzji i tym gorzej model pamięta szczegóły.

  • Wyniki narzędzi zapełniają okno szybciej niż Twoje prompty.
  • Zmieniasz zadanie: /clear. Zadanie się dłuży: /compact.
  • Research i przeszukiwanie kodu oddaj subagentom, żeby nie zaśmiecać głównego wątku.
Jeżeli macie ochotę wyrzucić komputer za okno, przeklinać, zwyzywać go, to jest moment na porzucenie sesji.
Łukasz Kałużny

Z dokumentacji Claude Code: „A clean session with a better prompt almost always outperforms a long session with accumulated corrections.”

Pytania z końcówki

  • Superpowers czy skille Pococka?

    Opinia Łukasza: Pocock. Lekkie, inżynierskie podejście, które nie narzuca się w repozytorium. Superpowers wyglądają dobrze na początku, potem brakuje im struktury.

  • Tokeny kończą się za szybko. Co robić?

    Minimalny setup: mało skilli i mało serwerów MCP. Precyzyjny spec, żeby agent nie przeszukiwał kodu. Subagenci używani świadomie. Do tego RTK.

  • Claude, Codex czy Copilot?

    Używasz tego, co masz dostępne i na co masz limity. Reszta to preferencje.

  • Jak reviewować testy od agenta?

    Scenariusze w stylu BDD i analiza statyczna zawsze włączona. Model danych i kontrakty definiujesz z góry. Te praktyki są starsze niż AI: „Extreme Programming Explained” to rok 1999.

Godzina to za mało. Te tematy rozkładamy w podcaście na czynniki pierwsze, bez zbędnego żargonu i BS.
